The two _training_loop threads are juniper-canopy's demo mode (src/demo_mode.py: threading.Thread(target=
self._training_loop, daemon=True)), which earlier tests started and left running. The sample of run 2 shows the
same three threads, under the same names, in the same frames.

Experiment, same env: validate_envs.py canopy --phase test --lane unit --env OMP_NUM_THREADS=6. Six is torch's
intra-op default on this host, so every thread's OpenMP count then agrees with it. The lane ran to the end in
512 s: 7959 tests, 7947 passed, 10 skipped, 2 failed (both are E-REQ), coverage 96.69%.

A synthetic script with three threads calling the same BLAS entry points
(util/ad-hoc/2026-10-20_turing_e2_blas_concurrency_repro.py) did not hang in this env or in JuniperCascor1.

The fix, the spec as it now stands (MKL; torch BLAS_INFO=mkl), run with no override: 7959 tests, 7947 passed,
10 skipped, 2 failed (E-REQ), coverage 96.68%, 558 s. JuniperCanopy1.summary.json is that run.
