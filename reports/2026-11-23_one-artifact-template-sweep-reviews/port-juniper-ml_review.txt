F1  MINOR  docs/REFERENCE.md:10116; notes/JUNIPER_2026-06-18_JUNIPER-ECOSYSTEM_PYPI-PUBLISH-PROCEDURE.md:712 (and the
           PR body's ladder bullet)
  What is wrong: "A TestPyPI job that failed on index lag is re-run instead ("Re-run failed jobs" on the release run,
  within 30 days): the re-run uploads the same bytes, which the index accepts, and repeats both checks." The notes
  amendment says the same. Since ruling 2 there are TWO TestPyPI jobs. When the one that failed on lag is
  `Verify the TestPyPI install`, "Re-run failed jobs" re-runs that job and the PyPI job after it. `Publish to TestPyPI`
  succeeded and is carried over, so nothing is uploaded again and only the install check repeats. This is the
  simple-index lag case the install check's own error names ("... after N tries (index lag?)").
  The recovery prescribed is right in both cases, so it cannot send an operator to a wrong rung. The description of
  what the re-run does is false for one of the two jobs.
  Shown by: the head's needs graph (verify-testpypi-install needs the TestPyPI job, and PyPI needs both).
  juniper-cascor docs/ci_cd/MANUAL.md:709 states it precisely: "A re-run `Publish to TestPyPI` uploads the same
  bytes ... and repeats its JSON check; the install check then runs again." The imprecise wording comes from
  SWEEP_BRIEF item D itself.
  Fix (both places): "... "Re-run failed jobs" on the release run, within 30 days: it runs the failed job and those
  after it again. A re-run `Publish to TestPyPI` uploads the same bytes, which the index accepts, and repeats its JSON
  check; the install check then runs again." The same edit applies to the PR body's ladder bullet.

  Shown by: mutation M14 (docs/REFERENCE.md:10101 "(four waits, ~40s)" -> the pre-sweep "(five waits, ~50s)"). All
  four suites pass, and the checker passes (7 of 7).
  Fix: state the figures in digits ("4 waits, ~40s"; "~60s") and pin them from the workflows in
  test_the_install_checks_retry. A sub-package makes tries-1 waits, since its error branch exits before the last
  sleep; the meta-package waits after each of its tries. For example:
  assertIn(f"{sub_tries - 1} waits, ~{(sub_tries - 1) * sub_waits[0]}s", reference) and
