## §2 Method

**Evaluation.** Ten parallel evaluators, one shared brief, each owning a slice (juniper-ml docs ×2, tests ×2; juniper-data docs, tests; juniper-canopy docs, tests; cascor + deploy; the three client repos). For every PR: the true delta against current `main` (`git merge-tree`, carried commits dropped); redundancy and duplicate adjudication across all 116; **tests re-run on `main`** in the repo's real environment, with one-line mutations of the code under test to prove non-vacuity (every mutated file restored byte-for-byte); **every docs claim re-derived from the code**; fixes reproduced on `main`. Each PR got a quality (SOLID / WEAK / BROKEN), a priority (P1 real defect / security / gate; P2 risky untested behaviour or a live operator contract; P3 low-risk) and a verdict. Each evaluator then prepared the accepted content, corrected, as an uncommitted patch on `main`, with the repo's pinned pre-commit and the relevant suites green.

**Landing.** Local `git commit` cannot sign headless (YubiKey), and `required_signatures` is on everywhere, so every commit is GitHub-signed through GraphQL `createCommitOnBranch`:

- A PR whose content stands alone **merged as itself** — unchanged ones by server-side `update-branch`; corrected ones **re-cut on current `main` as one signed commit** (`util/ad-hoc/2026-10-08_fleet_flood3_reset_pr_branch.py`: temp branch at `main`, signed commit, force-move of the PR head, guarded on the branch tip), with the fleet author kept as co-author.
- Clusters that collide (the docs PRs everywhere; juniper-ml's test PRs, which all edit the same three hand-maintained CI lists) and canopy's test PRs (~20 min CI per strict-lane cycle) were **consolidated into one PR per repo**, built from the evaluators' patches on fresh `main`.
- Native auto-merge (squash) armed on everything; `util/ad-hoc/2026-09-05_auto_merge_shepherd.py` re-synced one PR at a time per repo.
- A carried or superseded PR was closed **only after its carrier merged**, with a comment naming the carrier and the evaluation (`util/ad-hoc/2026-10-08_fleet_flood3_disposition_render.py --closes` + `util/ad-hoc/2026-10-08_fleet_flood3_pr_actions.py close`). Closing is not destructive: GitHub keeps a closed PR's diff.

## §3 What the evaluation found

- **Tests were behavioural, again.** Every carried suite fails under one-line mutations of the code it pins (e.g. 81/81 + 6/6 in one juniper-ml slice, 44/44 in canopy, 25/25 in the client repos). Round 2's figure (88%) holds up.
- **But about one in five of the 57 test PRs was broken or mis-shaped beyond lint as submitted** (and many others failed lint) — in ways CI never showed, because CI never ran them:
  - *global state leaks*: canopy#715 replaced `time.monotonic` / `time.sleep` on the global `time` module and never restored them, failing five unrelated tests on every leg;
  - *platform assumptions*: GNU `base64 -w0` and `date -d` inside `$(…)` (which `set -e` does not catch) made the required macOS leg fail deterministically (data#458, #467; data-client#221);
  - *interpreter assumptions*: an unclosed synthetic `HTTPError` under Python 3.14 + `filterwarnings=error` (deploy#241); a `requests` stand-in lacking `Session` that crashed at import on 3.12/3.13 (ml#2143);
  - *repo policy*: a suite that executed the watchdog deploy script, which `tests/test_yamaguchi_watchdog.py` forbids (ml#2138); raw `os.environ.copy()` that `tests/test_env_repr_safety.py` forbids (ml#2159);
  - *lint*: black / mypy / bandit / flake8 findings that failed `Pre-commit` and hid everything else.
- **Docs were well-grounded and stale.** As in round 2, almost every false claim was a snapshot that had been true when the branch was cut (a PR saying "#702 is not merged yet" written twelve minutes before #702 merged). One systematic error recurred in **five repos**: "`contains()` is case-sensitive, so `@Claude` does not start the job" — false (GitHub's `contains()` ignores case and the action's phrase match is case-insensitive). One docs PR (ml#2141) asserted the opposite of the consensus record that merged after it was cut, and was closed.
- **Three real fixes**: canopy#721 (P1, below), data#454 (FastAPI 0.142 native-telemetry opt-out — hardening, not a live leak), and ml#2129 (already landed as ml#2134, which supersedes it).

## §6 Process traps hit during the disposition

- **A PR's head can stop tracking its branch.** canopy#721's PR object reported head `973c8680` while `cursor/missing-test-coverage-7a79` had moved to a lockfile auto-regen commit `033d7311` (pushed 2026-10-05 14:29Z, during that day's GitHub incident) that GitHub never synced into the PR. Read the branch tip from `git/ref`, not the PR object — the re-cut tool's `--expect-tip` guard does.
- **A "stacked" PR refuses every ordinary merge path, even after its base became `main`.** data#454 was opened by Copilot from a review comment on #446, and GitHub kept it registered in a stack after #446 merged: `enablePullRequestAutoMerge` answered "Auto-merge is not supported for stacked pull requests" (while `viewerCanEnableAutoMerge` read `true`), `PUT …/pulls/454/update-branch` answered 403 "Updating a stacked PR's branch via this endpoint is not supported", and `PUT …/pulls/454/merge` answered 403 "Merging stacked PRs via this endpoint is not supported". What works: keep the branch current by re-cutting it (a ref force-move is not update-branch), wait for green, then **`PUT /repos/{owner}/{repo}/pulls/{n}/merge-async`** (`merge_method=squash`, `merge_action=direct_merge`, `sha=<head>`, `bypass_rules` left false) and poll `GET …/merge-async/{uuid}`. That endpoint merges **all open downstack PRs** with it — check the stack has none (here #446 was already merged).
- **HTTP 499 on a large `createCommitOnBranch`** (data#475's 11-file commit) created the branch at `main` and landed no commit. Check the ref, then append with `util/ad-hoc/2026-09-08_push_signed_commit.py` and open the PR with `gh pr create` (the same trap is recorded in the agent memory file `reference_signed_commit_api_499_on_large_payloads.md`).
- **A repo-wide lint suite judges new files.** ml#2182 first failed CI on `tests/test_env_repr_safety.py`, which scans every test file for raw `os.environ` mappings — the harvest had run its 25 new suites and the wiring gates, not the full list. After the fix, all 198 suites were run locally, one process each, as CI does.
- **Green checks are not mergeable.** ml#2182 then sat `BLOCKED` with every required context passing: CodeQL had posted five review threads on the harvested suites (`unittest` imported both ways in four files; `assertTrue(a <= b)` on two sets), and the conversation-resolution rule blocks on any unresolved thread. Fixing the code (`import unittest.mock as mock`, `assertLessEqual`) cleared all five threads without a manual resolve. Screen new Python with `util/ad-hoc/2026-10-05_codeql_python_prescreen.py` before opening the PR — this record's own tooling was screened that way (five predicted alerts fixed first) — **but the prescreen models only a subset of the rules.** CodeQL still raised three on this record's own PR (ml#2185), none of which it predicts: two `py/clear-text-logging-sensitive-data` because a constant *named* `SECRETS` held a file path (`util/check_image_no_secrets.py`) that was later printed — the sensitivity heuristic reads the name, not the value — and one `py/multiple-definition` (a dead `verdict = "?"` initialiser). Renaming the constant and dropping the dead line cleared them. A clean prescreen means "none of the modelled rules", not "no alerts".
- **A skip guard can measure the wrong thing.** data-client#221's re-cut skipped its byte-level assertion when `base64 -w0` failed on empty stdin; on the macOS runner that probe passed while the step's real form, `base64 -w0 <file>`, still produced an empty payload, so the required macOS leg failed. The guard now runs the step's exact form on a one-byte file and checks the output is `eA==` (never skipping on Linux) — the probe juniper-data's equivalent suite already used, which had passed macOS. Probe the question the code under test asks, by output, not by exit code.
- **Time-box evaluators.** One evaluator spent 5.5 hours on twelve docs PRs and verified five; the remaining seven were re-split across two evaluators with a ~40-minute box and finished in ~20 minutes each.
- **A named carrier slot that resolves to nothing must block a close.** The first renderer draft treated an unopened consolidation as "no carrier", which would have closed canopy and juniper-ml docs PRs ungated; caught on the dry run, before any close.
- **A PR that touches `pyproject.toml` cannot keep a targeted lock** (2026-10-10, item 3).
  - **The trigger.** In juniper-data, juniper-canopy and juniper-cascor, `lockfile-update.yml` runs on every same-repo `pull_request` whose diff contains `pyproject.toml`. It skips only `release/` branches, and it regenerates with `--upgrade`.
  - **What it did.** The first versions of juniper-data#478, juniper-canopy#739 and juniper-cascor#711 raised two floors beside a two-pin lock. Each got a full regen pushed onto its branch: about 30 unrelated moves in data, including `huggingface-hub` 1.33 -> 2.2 and `httpx` -> `httpx2`.
  - **The fix.**
    - Disarm auto-merge at once. An armed net merges whatever head is current. `util/safe_merge.py`'s local path refused ("head moved during the wait") and disarmed its own net.
    - Re-cut each PR as lock + CHANGELOG only (`2026-10-08_fleet_flood3_reset_pr_branch.py`).
    - Carry the floors in the `release/` bump PRs.
  - juniper-recurrence has no such workflow; #199 merged with its floors.
- **A ceremony archive PR arms itself before its placeholders can be filled.** For juniper-data 0.17.1 (juniper-ml#2215) and juniper-cascor 0.12.0 (juniper-ml#2216), each archive PR was disarmed as soon as it appeared. The Release body (`gh release edit`) and the archive branch (`util/push_signed_commit.py`) were then filled with the same text, and the PR re-armed.
- **A `pypi` gate left waiting expires** (2026-10-23, item 3). GitHub cancels a workflow run at 35 days, and that count includes time spent waiting for approval. A run can be re-run only within 30 days of its start (docs.github.com/en/actions/reference/limits). The environment docs give only the wait-timer maximum, so they are the wrong place to look.
  - juniper-data 0.17.1 and juniper-cascor 0.12.0 waited at their gates from 2026-10-10. Their re-run window would have closed on 2026-11-09, and both runs would have been cancelled around 2026-11-14.
  - TestPyPI already held both versions and does not accept a re-upload, so a cancelled run would have meant new version numbers.
  - The owner approved both inside the window, on 2026-10-23 and 2026-10-25. When handing a gate over, quote both dates, computed from the run's `created_at`.
- **Making a swallowed failure loud can break a test that passed only because of it** (2026-10-26, juniper-data#498).
  - juniper-data's suite runs the lockfile commit step on the REQUIRED macOS leg, where BSD `base64` has no `-w0`. Before the base64 fix the step "passed" there by committing an empty payload; after it, the encode stops the step (exit 64) and the leg went red.
  - The remedy is in the tests, not the workflow (which runs only on `ubuntu-latest`): juniper-data#498 and juniper-data-client#248 install a stand-in for exactly `base64 -w0 FILE` when the runner's `base64` fails a probe of that form. A BSD-like simulation without the stand-in reproduces CI's failures, so the pass is not vacuous. Skipping macOS would have hidden the platform from the one check that proved useful.
- **A worktree-isolated session can remove sibling worktrees but cannot inspect `.claude/worktrees/agent-*`** (2026-10-26 cleanup).
  - `git worktree remove --force <literal path>` is allowed from the session's own worktree, and `cd <a non-target centralized worktree> && git worktree remove …` for the siblings. `cd` into an agent worktree to run a status is refused.
  - So the dirty test is git's own refusal (`remove` without `--force`), then `util/ad-hoc/2026-10-26_worktree_blob_classify.py`, which hashes the files and compares them with `main` and with every object in `main`'s history. Only a blob that never existed on `main` (UNIQUE) needs preserving before `--force` deletes it, ignored files included.
  - An mtime test ("newer than the `.git` pointer") is useless: a checkout writes every tracked file after the pointer.
- **`safe_merge.py` ended twice without merging, and a re-run fixed both** (2026-10-26). GitHub's GraphQL answered two merges with "Something went wrong while executing your query": the log ended `ERROR: gh pr merge … failed`, with exit 0 and the PR still CLEAN. And juniper-canopy's CI outlasted the 3000 s window (`absent: Quality Gate`), so the net was disarmed; the gate went green minutes later. Read the `MERGED` line, never the exit status.
- **`JUNIPER_DRIFT_TEST_FORCE_LOCAL=1` from a centralized worktree reads the lagging primaries.** `tests/test_service_fork_drift.py` finds sibling repos by walking up from its own file, so from `worktrees/` it reaches the parent `Juniper/` directory and silently checks the primary checkouts instead of skipping. juniper-ml#2365 ran it against a scratch root of fresh clones.
- **A dependency release can turn `main` red with no commit** (2026-10-27).
  - pytest 9.2.0 reached PyPI at 21:30Z. cascor's next CI run failed every unit leg, on a test that read a private pytest attribute. `main`'s HEAD was the green dateutil bump.
  - The release train's gate caught it. The ceremony refuses a red `main`, and the bump PR's own CI would have failed the same way.
  - Read a red `main`'s log for the installed versions before blaming the head commit. A test that reaches into a tool's internals breaks on the tool's minor releases; ask the tool's public API instead.
- **A predecessor session may already have acted on the owner's request** (2026-10-27). The owner approved the cleanup in this session, and the predecessor had already removed 17 of its 18 worktrees on the same request.
  - The cue was the inventory's paths being gone, discovered before any removal ran.
  - Re-list the targets before acting on an inherited inventory. A predecessor that is still alive holds its own worktree's lock: wait until its process has exited, then compare its files with the preserved copies.
  - **A re-list can also find LESS than the inventory** (2026-10-29). Two of the six worktrees that `HANDOFF_2026-10-28_flood3-continuation-cascor-0-13-0-at-pypi-gate.md` listed, `agent-a8ac272b0d644d1b6` and `agent-a84219c62702dc20b`, were gone, with no removal record in any `tmp/worktree-cleanup-*` folder and no local branch left. Whatever the second one's `tmp/` held (PR bodies, check-watch output) is lost.
- **A preservation tool's count is not the check; a whole-tree diff is** (2026-10-29).
  - `2026-10-26_worktree_blob_classify.py` skips every image and PDF suffix (its `LFS_EXT`), untracked files included, so `2026-10-26_worktree_preserve_unique.py` never saw them. Here that was five untracked files, three of them juniper-ml#2381's evidence plots (`tmp/issue2064/eval_metrics_*.png`).
  - `diff -rq` of each preserved tree against its source caught them; they were copied by hand. A sweep of the four targets for those suffixes found 137 files, 132 of them tracked.
  - The ml lane's worktree then went with a plain `git worktree remove`, no `--force` and no refusal: everything it held was ignored, and git deletes ignored files without asking. So git's refusal (the 2026-10-26 bullet above) is no dirty test for a worktree whose unique files are all ignored.
- **A holder check that reads `cmdline` holds itself.** The shell that launches it carries the targets in its own argv, so a naive scan reports every target HELD by its launcher. Skipping the parent is not enough: piped into `grep`, the shell forks a subshell that keeps the launcher's cmdline without being an ancestor (`| cat` read clear, `| grep` read HELD). `2026-10-29_worktree_holder_check.py` skips the cmdline of every ancestor and of every process whose cmdline is identical to an ancestor's; their cwd and other views still count, and the session's own worktree is the positive control. The removal verdicts were taken unpiped, where only the direct parent matched.
- **A pip torch does not import on the Linux host** while `LD_LIBRARY_PATH` names rust_mudgeon's libtorch: `libtorch_python.so: undefined symbol: _PyObject_NextNotImplemented`. The import probe runs under `env -u LD_LIBRARY_PATH -u LIBTORCH`.
- **A secret reaches only the steps that pass it** (2026-10-29). The owner added `CODECOV_TOKEN` to all nine repositories' Actions secrets. juniper-canopy's Codecov step had no `token:` input, so its uploads would have stayed refused with the secret present. juniper-canopy#779 added the input before any canopy run could show it: no `ci.yml` run fell between the secret (22:11Z) and #779's. No Dependabot store holds the token, so a Dependabot PR's upload is still tokenless.
- **A workflow comment can fail a required lint** (2026-10-29). cascor's `Documentation Links` job runs juniper-ci-tools' workflow-path lint. It reads any slash path ending in `.py` in a workflow's `run:` text as a repository script, comments included. juniper-cascor#735's first ruling commit cited `pytest_benchmark/fixture.py:88` in a comment and went red. Pre-commit does not run that lint.
- **A duplicate background session is stopped with `claude stop <id>`** (2026-10-30). `claude agents --json` gave the duplicate continuation's id, `2fc3f4e1`, with status `waiting`. `claude stop 2fc3f4e1` ended it: its process and its MCP servers exited. Its conversation is kept, so `claude attach 2fc3f4e1` could reopen it. **Never do that to a stopped duplicate:** it would resume believing it holds merge approval, with its stale dialog and its undelivered messages. Its worktree's lock line outlived the process briefly. It still named the dead pid at 18:46:11Z, two seconds after the stop, and was gone by 18:50:11Z, when the worktree's admin directory last changed; what removed it is unrecorded. So a lock line is no liveness test in either direction: compare `/proc/<pid>/stat`'s start time with the lock's, and expect the lock to vanish on its own. `claude rm <id>` removes the session and its worktree, and with it the worktree's ignored `tmp/`, so preserve that first.
- **GitHub can fail one run's job list on every request** (2026-10-30). cascor's SARIF survey aborted (exit 2) in all five repositories it was pointed at. `GET /repos/<repo>/actions/runs/<id>/jobs` answered HTTP 502 for some runs on every attempt, at any page size, while `GET …/runs/<id>` loaded, and githubstatus read "All Systems Operational". A re-run failed on different runs. Later the runs that had failed every time loaded too (16 and 19 jobs), so the 502s were transient but outlasted the survey's four attempts. Aborting is the right default for a survey. `util/ad-hoc/2026-10-30_bandit_sarif_upload_survey_tolerant.py` runs it unchanged except that such a run is tallied `unreadable`, never counted as an upload.
- **In an LFS repository, every image on disk differs from its tree entry** (2026-10-30). The tree holds LFS pointer blobs, so a blob comparison calls all of them modified: a test run of the keep-evidence driver on one juniper-ml target copied all 99 LFS images. Compare an LFS file's sha256 with `git lfs ls-files -l <base>`; that run then kept exactly the 17 `tmp/` files the inventory named. Test a preservation tool on one small target before the real run. Of the four repositories the ten targets came from, only juniper-ml tracked any LFS file at the targets' base commits.
- **A copier that walks files does not create an empty directory** (2026-10-30). The whole-tree `diff -rq` that §6 asks for reported one `Only in` line: `bench-probe/.benchmarks`, an empty pytest-benchmark store. It was recreated in the copy and the diff re-run clean. An `Only in` line still needs a look at what it names.
- **The jobs API reports a step's conclusion after `continue-on-error`** (2026-10-30). GitHub's contexts distinguish `outcome` (before `continue-on-error`) from `conclusion` (after), and `GET …/actions/runs/<id>/jobs` exposes only the latter, so a masked failure reads `success`. juniper-canopy job 123689681187's upload logged `##[error]Path does not exist: reports/security/bandit.sarif`, and its step reads `success`. Its check run's annotations still list `failure: Path does not exist: …`. So a survey that counts failed steps by `conclusion` is blind exactly where `continue-on-error` hides a failure. Count by an effect instead, such as the `Bandit` check the upload should create, or by the check run's error annotations. cascor's 2026-10-27 survey counted "165 of 165 succeeded" that way (§4, the new cascor row).
