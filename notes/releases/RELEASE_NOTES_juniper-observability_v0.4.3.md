## What's New

### Fixed

- **`configure_sentry` works on sentry-sdk 3.x, and the `sentry` and `test` extras admit it
  (`sentry-sdk[fastapi]>=2.35.0,<4`).** sentry-sdk 3.0.0 (PyPI, 2026-11-23 09:30Z) removed four of
  the options `configure_sentry` passed (`send_default_pii`, `include_local_variables`,
  `enable_logs` and `before_send_transaction`), and its `sentry_sdk.init` raises
  `TypeError: Unknown option 'send_default_pii'`. The published 0.4.2 admits 3.x, so a fresh
  `[sentry]` install raised at startup whenever a DSN was set, and 20 tests in `tests/test_sentry.py`
  failed. juniper-ml#2608 capped the extras below 3 on `main`; that cap never shipped, and this
  replaces it (Overtoad ruling, 2026-11-24). The installed SDK's major decides which options are
  passed. On 2.x they are unchanged. On 3.x:
  - `data_collection` carries the same choices. `user_info` is
    `send_pii`. Without `send_pii` no cookie is collected, and with it only the cookies' names. The
    request-header denylist also names the seven headers the hook scrubs, and without `send_pii`
    `X-Forwarded-For` and `X-Real-IP` too: 2.x removed both unless `send_default_pii` was on, and
    3.x's denylist matches neither. `stack_frame_variables` is off. With the SDK's defaults, 3.0.0
    sent every frame's locals (the request's raw headers among them) and the client's address.
  - 3.0.0 deleted 2.x's `EventScrubber`, which by default redacted denylisted names (`password`,
    `api_key`, `token` ...) in request headers, request bodies, `extra`, `user`, breadcrumb data and
    span data, and without `send_default_pii` also its PII names (`ip_address`, `remote_addr`,
    `x_forwarded_for`, `x_real_ip`). On 3.x the hooks apply both of 2.76.0's lists themselves, the PII
    one unless the active client is the one `configure_sentry(send_pii=True)` made and its `user_info`
    is on: a later `sentry_sdk.init` gets 2.x's default, no PII. On 2.x they leave those containers to
    the SDK, so what 2.x sends is unchanged on every 2.x: 2.35.0 matches names without reading `-` as
    `_`, so a second pass there would have changed it. `data_collection` also turns
    off what 2.x did not collect without `send_default_pii` and 3.x's defaults do: SQL parameters
    and redis arguments (never), queue job arguments, GenAI and MCP inputs and outputs, GraphQL
    documents and variables (only with `send_pii`). 3.x sends no request bodies until R-OBS-SC-3
    decides them, and `attach_stacktrace` is off, as on 2.x. A sentry-sdk major other than 2 or 3,
    or a `VERSION` that does not start with ASCII digits, initialises nothing. A stand-in module
    without a string `VERSION` (juniper-data's and juniper-cascor's tests use one; a `MagicMock` is
    one too) gets 0.4.2's options.
  - 3.x streams spans in place of transactions, and the server span carries each request header as
    an `http.request.header.<name>` attribute. A second hook, installed as `before_send_span`,
    filters the seven headers there. The SDK's denylist matches no term in
    `sec-websocket-protocol`, so with its defaults juniper-canopy's WebSocket key reached every span,
    and every error event, raw (measured on 3.0.0). The hook never raises and always returns the
    span: 3.0.0 sends the original span when `before_send_span` raises.
  - 3.x installs no logging integration by default, so an ERROR record became neither an error
    event nor a Sentry Log. `configure_sentry` passes it with `event_level=logging.ERROR`, which is
    how 2.x behaved by default.
  - Left to R-OBS-SC-3, as before: query strings, Sentry Logs, request bodies, breadcrumbs and
    exception values. On 3.x the SDK's own denylist filters a query parameter whose name matches it
    (`?api_key=` among them); 2.x sends the query string raw.
- Pinned in `tests/test_sentry.py`, which holds 197 tests where it held 75. The option tests check
  both majors' options whichever SDK is installed, and the wire tests run the installed SDK. CI runs
  them under both majors: the `test` job resolves 3.x, and a new `test-sentry-sdk-2` job holds
  sentry-sdk below 3, which resolves the newest 2.x (the 2.35.0 floor is tested locally, not in CI). `util/ad-hoc/2026-11-24_sentry_sdk_major_wire_probe.py` in juniper-ml prints what each
  item carries on either major.

## Known Issues

These predate 0.4.3, which leaves them as 0.4.2 had them. The next release, 0.4.4 (R-OBS-SC-3), is to decide them. juniper-deploy's defaults configure no Sentry DSN, so none of them sends anything until an operator sets one. Each was measured on the wire on sentry-sdk 2.35.0, 2.76.0 and 3.0.0, under either `send_pii` value, by juniper-ml's `util/ad-hoc/2026-11-26_observability_known_issues_wire_probe.py`.

- **The client's address, through five proxy headers, even without `send_pii`.** `Forwarded`, `X-Client-IP`, `CF-Connecting-IP`, `True-Client-IP` and `X-Cluster-Client-IP` reach the error events and sampled transactions (on 3.x, spans) of a request that carries them, raw. Of the headers that carry a client address, only `X-Forwarded-For` and `X-Real-IP` are filtered.
- **On 2.x, a request-body field whose name the denylist lacks.** juniper-canopy's `POST /api/remote/connect` carries its worker `authkey` in the JSON body. Its pydantic `SecretStr` hides it from logs and reprs, not from the raw body the SDK reads, so it reaches `request.data` in error events and in every sampled transaction. 3.x sends no request bodies.
- **Sentry Logs carry a log record's `extra` fields raw**, on either major, even under a name the denylist names (`api_key`): `configure_sentry` installs no `before_send_log` hook.
